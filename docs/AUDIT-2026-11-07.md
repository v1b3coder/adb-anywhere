# Audit — completeness, correctness, security, firewall threat surface

Date: 2026-11-07
App commit: `8190bcf`
Scope: the app (Kotlin/Compose), the vendored `adbd` fork and its patch set,
the firewall design in `docs/FIREWALL.md`, the build/CI/release setup and the
tests. DESIGN.md and docs/FIREWALL.md are treated as the specification.

**Verdict: the control plane is in good shape and the firewall is a real,
well-scoped design, but the firewall has three exploitable policy defects and two
fail-open paths. It is not ready to be described as a security boundary.**

What I ran:

```text
./gradlew :app:testDebugUnitTest    BUILD SUCCESSFUL, 74 tests, 0 failures
./gradlew :app:lintDebug            0 errors, 0 fatal; 11 warnings (3 security)
```

Not run: any device/emulator, the `adbd` rebuild, the firewall e2e script, or a
re-vendor check. The daemon claims below are read from the vendored sources and
the patches; the app claims are read from source and the JVM tests.

## 1. Threat surface of the firewall design

### 1.1 Assets

| Asset | Why it matters | Where it lives |
|---|---|---|
| ADB shell as `uid=2000(shell)` | Full read of `/sdcard`, `run-as` for debuggable apps, `pm`/`am`/`settings`, screenshots, `tcp:`/`reverse:` pivots | `adbd` child process |
| App ADB identity | Opens the loopback channel and bootstraps the system adbd | `/data/user_de/0/<pkg>/files/appkey.pk8` |
| Developer machine keys | Who may connect | `/data/local/tmp/adb-anywhere/adb_keys`, shell-owned `0600` |
| `WRITE_SECURE_SETTINGS` grant | Toggles `ADB_ENABLED`, `adb_wifi_enabled`, `adb_allowed_connection_time` | App permission, granted once over shell |
| Firewall configuration and audit log | Policy and a record of calls | Device-protected prefs and `firewall-audit.jsonl` |

### 1.2 Actors

| Actor | Capability assumed |
|---|---|
| Paired developer machine | Has a private key in the key file; may open every service |
| VPN peer on the IP allowlist without a key | Can reach `<vpn-ip>:<vpn-port>`; can send ADB frames; cannot authenticate |
| Malicious local app | Can reach `127.0.0.1:<loopback>`; can bind a port first; can draw overlays; can read its own UID's data |
| Shell user / compromised developer key | Can read and rewrite the key file; can start a second `adbd` with any `--listen`; can write `/data/local/tmp` |
| VPN app | Owns the outer network boundary; can route the VPN address to the LAN or internet |
| OEM framework / system adbd | Can ignore a setting write; can keep the TLS listener up; can expose 5555 |
| The user | The only authorization oracle for an unmatched call |

### 1.3 Entry points and trust boundaries

| # | Entry point | Who can reach it | What stops them | Residual risk |
|---|---|---|---|---|
| B1 | VPN ACL (outer boundary) | The VPN app | Nothing the app controls | The app trusts the VPN app to keep the address private |
| B2 | `<vpn-ip>:<vpn-port>` relay listener | Any peer the VPN delivers packets to | IP allowlist (optional), app allowlist (optional), 8/2 connection caps | Pre-auth: the relay reads frames and can prompt before ADB auth; a silent peer holds a slot |
| B3 | `127.0.0.1:<loopback>` patched `adbd` | Any local app | ADB RSA key auth against the key file | A local app can bind the port first and impersonate the daemon |
| B4 | Key file `/data/local/tmp/adb-anywhere/adb_keys` | Any process with `shell` | File mode `0600` | Shell can read and rewrite it; the app cannot stop that |
| B5 | The relay parser in the app process | Every relayed byte | The parser itself | A parser bug is a firewall bypass; a parser crash drops sessions |
| B6 | The approval prompt (overlay/notification/activity) | The user | The user's tap, a 30 s timeout, screen-off/locked deny | Tapjacking, prompt spam, no key attribution |
| B7 | The app's own loopback shell | The app | The app key | Not filtered by design; the app can run any shell command |
| B8 | The system adbd's TLS/5555 listeners | Every interface on the network | `adb_wifi_enabled=0` after setup; `ADB_ENABLED` | A failed setup or an OEM can leave them up; the app only warns |
| B9 | Device-protected prefs and audit log | The app, a debug `run-as` build | App sandbox | The audit log is plaintext and not tamper-evident |

### 1.4 What the firewall actually enforces

1. **A single owner for the VPN port.** With the firewall on, `adbd` binds only
   loopback and the app relay owns `<vpn-ip>:<vpn-port>`; the mode is recorded in
   `daemonFirewallMode` and the port is the authority (`docs/FIREWALL.md` §2, §9).
2. **A peer gate before any ADB byte.** The relay checks the IP allowlist and the
   foreground-app allowlist immediately after `accept()`, before reading a frame.
3. **A per-call gate at `A_OPEN`.** `CallRules` applies built-in denies,
   first-match user rules, then a prompt or a deny.
4. **A byte-transparent relay.** ADB key auth stays end-to-end between the
   developer machine and `adbd`; the relay never authenticates or rewrites.
5. **An audit trail.** Every accept, deny, prompt, allow and close is a JSON line,
   bounded and rotated.
6. **A hard denial for the services the daemon rejects and for `A_STLS`.**

### 1.5 What it does not enforce

- **A second authentication factor.** ADB key auth is the only authentication.
  The relay cannot see which key authenticated, so the prompt cannot show the key
  label or fingerprint, and `auth_ok`/`auth_unknown` are not recorded. The design
  lists this as deferred; it is a security gap, not a cosmetic one.
- **A sandbox for `shell`.** A shell is a shell. The call policy is lexical and
  advisory; `sh -c`, `toybox`, symlinks and `..` are outside its reach.
- **Protection from a compromised VPN peer that is on the IP allowlist and has a
  key.** That peer has the same shell as before, minus the call policy.
- **Protection from a local app with the app key, or from a shell user.** The key
  file is shell-writable, so the shell user can add a key; the app cannot prevent
  it without a system-privileged component.
- **Protection from a malicious local app that binds the relay address first.**
  The relay reports a bind failure and does not fall back.
- **Protection from a VPN that routes the VPN address to the LAN/internet.** The
  app cannot verify the VPN ACL; this is the outer boundary and it is trusted.
- **Filtering of the app's own loopback channel.** By design.
- **A general network firewall.** Only the app's one listener is filtered.

### 1.6 Conditions that widen the surface

| Condition | Effect |
|---|---|
| Firewall off (default) | `adbd` owns `<vpn-ip>:<vpn-port>` directly; only the VPN ACL and the key file gate it. |
| IP allowlist off (default) | Any peer the VPN delivers to can connect; only the key file gates it. |
| App allowlist off (default) | ADB is available while any app is foreground. |
| Call policy off (default) | Every parsed call is allowed; only key auth gates it. |
| Prompts disabled (`promptTimeoutMs=0`) | Unmatched calls are denied; the mode is not reachable from the UI. |
| Failed setup after the Wi-Fi bootstrap | The system TLS listener stays on all interfaces (finding H3). |
| `UsageStats` revoked | The app allowlist fails open on the last known app (finding H4). |
| System adbd's 5555 listener | A residual listener outside the relay; warning only. |
| `dev:`/`local*:`/`vsock:` | Still accepted by `adbd`; the relay denies them only when call policy is on. |
| Debug build | Exported `DebugReceiver` and the `MainActivity` extras are a powerful surface. |

## 2. High findings

### H1 — A custom filter with action `Deny` allows the call

**Where:** `app/src/main/java/cz/slush/adbanywhere/firewall/AdbRelay.kt:163-177`
(and the same branch in `handleWrite` at `:225-230`).

**What happens:** `PromptResponse(PromptDecision.CUSTOM, rule)` is treated as an
allow whenever `rule != null`, without looking at `rule.action`. The custom-filter
editor lets the user choose `Deny` (`ui/RuleEditor.kt`), and the prompt's custom
filter path forwards that rule unchanged. So a user who opens *Custom filter*, picks
*Deny*, and saves gets the call **allowed** and a `DENY` rule persisted.

**Impact:** an explicit deny becomes an allow. This is a policy inversion on the one
screen the user trusts to make the decision, and the audit log records
`call_allowed`. It is silent and reproducible.

**Fix:** compute the verdict in one place. Either

- make `PromptResponse` carry an explicit `allowed: Boolean` (or the effective
  `CallDecision`) computed from `rule.action` in `FirewallPolicy.prompt`, or
- in the relay, branch on `response.rule?.action` for `CUSTOM`:
  `ALLOW` → forward, `DENY` → `deny(frame, call, rule.id)`.

Add two tests: custom `ALLOW` forwards the `A_OPEN`; custom `DENY` sends `A_CLSE`
and audits `call_denied`.

### H2 — The `sync:` path policy can be bypassed with a second frame

**Where:** `AdbRelay.kt:189-190` and `:301`. `handleWrite` evaluates only the
first client sync frame and clears `firstSyncFrame` *before* parsing. A first frame
that is `STAT`/`LSTAT`/`LIST` (legitimate and usually allowed) is evaluated; a
following `SEND`/`RECV` with any path is forwarded unchecked. A first frame that
fails to parse (for example a `DATA` frame or a path over 1024 bytes) also clears
the flag and disables the check for the whole stream.

**Impact:** the `sync:` path rule, the main way `adb push`/`adb pull` is gated, is
trivially bypassable by any authenticated peer. The attacker sends
`STAT /sdcard` then `SEND /data/local/tmp/evil`. The design's "path rules" are the
only protection for push/pull; symlinks and `..` are already documented as
advisory, but this bypass does not need either.

**Fix:** make the sync state machine per stream and evaluate every `SEND`/`RECV`
(and v2 setup) frame, not only the first. Keep `DATA` opaque. On a malformed or
non-direction first frame, close the stream (fail closed) instead of forwarding it.
Add a test: `STAT` with an allowed path, then `SEND` with a denied path → `A_CLSE`
and `call_denied`.

### H3 — A failed setup after the Wi-Fi bootstrap leaves the system TLS listener on

**Where:** `service/ControlService.kt:663-694` (`abortSetup`) and `:396-420`
(the bootstrap). `abortSetup` deliberately stops only the patched daemon and the
relay; it does not write `adb_wifi_enabled=0` and does not verify the TLS listener.
The bootstrap writes `adb_wifi_enabled=1` on a Wi-Fi start after a completed setup
(`prefs.setupComplete`). Any later failure (deploy, `grantSelfPermission`,
`verifyDaemon`, relay bind, `harden`) leaves the phone with the system TLS listener
on **all interfaces** and the app's own daemon stopped. On a first run the watchdog
loop is not started, so nothing retries or closes it.

This regresses the audit's P0-2 (`docs/AUDIT.md`), and it contradicts DESIGN.md
§2 ("never expose plain ADB on an untrusted LAN") and §8 ("system adbd ... not
reachable over TCP after `ADB_WIFI_ENABLED=0`"). TLS ADB is still ADB, and the
paired app key is enough to reach it. The UI warning (`AdbStatus.warnings()`) is the
only mitigation.

**Fix:** restore the pre-setup `AdbState` and, on a failure that has reached the
bootstrap, write and verify `adb_wifi_enabled=0` and the closed TLS port with
`WirelessDebuggingGuard` before reporting the error. The design's objection ("turning
it off cuts the connection the retry needs") is valid for a *transient* failure: keep
the bootstrap only while a bounded retry is in flight, and close it when the retry
gives up or the user stops. Add a test for the `setup` failure path (fake settings)
asserting `adb_wifi_enabled=0` after the failure.

### H4 — The app allowlist fails open when `UsageStats` is unavailable or revoked

**Where:** `firewall/ForegroundAppMonitor.kt:63-70`. `queryEvents` is wrapped in
`runCatching{}.getOrNull()`; on `null`, or on an empty result (which is what a
revoked `PACKAGE_USAGE_STATS` appop returns), the tracker is left unchanged and
`_state.value = tracker.state()` republishes the last known package. So the last
allowed app stays "foreground" forever, and external ADB stays open on every screen.
`AppViewModel.setAppAllowlistEnabled(true)` does not check the appop, and the UI only
offers a "Grant usage access" button.

The design (`docs/FIREWALL.md` §6) says: "If it is missing, the module cannot be
enabled and the UI says why." That is not implemented.

**Impact:** one of the three firewall modules silently degrades to "always allow the
last app" after a permission revocation or an OEM `UsageStats` failure. This is a
fail-open on a security control.

**Fix:** (1) check `AppOpsManager` `GET_USAGE_STATS` before enabling the module and
in `appAllowed()`; (2) when `queryEvents` returns no events for a full poll window,
treat the foreground as unknown (deny) instead of keeping the last value; (3) show a
persistent warning in the Firewall tab when the appop is missing; (4) add a test with
a fake monitor that returns no events.

### H5 — The prompt cannot distinguish an authenticated key, and unauthenticated peers can prompt

**Where:** `AdbRelay.handleOpen` evaluates policy for every `A_OPEN` and the relay
forwards `A_AUTH` untouched. `promptForCall` shows only the peer address and the raw
service string. The deferred item in `docs/FIREWALL.md` §16 ("Key fingerprint in the
prompt and `auth_ok`/`auth_unknown` audit events") is the only thing that would let
the user tell a paired machine from an unauthenticated peer. The prompt also does not
show the countdown that §7.5 promises.

**Impact:** a peer on the IP allowlist without a key can spam approval prompts
(8 pending, 30 s each), and the user has no way to see that the caller is not
authenticated. Prompt fatigue is the most likely way a user approves a call they
should not. It also holds the app-allowlist grace timer suspended (finding H6).

**Fix:** watch `A_AUTH`/`A_CNXN` on each relayed connection and mark it
authenticated only after the server sends `A_CNXN`; do not prompt (and close the
`A_OPEN`) on an unauthenticated transport. Parse the key from `A_AUTH` and show its
label/fingerprint in the prompt, and record `auth_ok`/`auth_unknown` in the audit
log. At minimum, close `A_OPEN`s that arrive before auth and add a test that an
`A_OPEN` before `A_CNXN` is denied without a prompt.

### H6 — A cancelled prompt leaks its slot and suspends the app-allowlist grace timer

**Where:** `service/ControlService.kt:1026-1035`. The `finally` starts with
`withContext(Dispatchers.Main) { promptOverlay?.hide() }`. When the calling
coroutine (the relay's scope) is cancelled — the client closes the connection, the
relay is stopped or the firewall is toggled — `withContext` throws
`CancellationException` and the remaining cleanup (`prompts.remove`,
`pendingPrompt` clear, `ControlBus.update`, `onPromptFinished`) is skipped. Then
`FirewallProxy.onForegroundChanged` (`:218`) returns early while
`policy.promptPending()` is true, so the grace timer never runs and live sessions
stay open while the allowed app is not foreground.

**Impact:** a peer with a key can defeat the app allowlist's live-session closure by
opening an unmatched call, getting a prompt, and closing the connection. The prompt
slot stays in `prompts` forever (until `stopFirewall`), `pendingPrompts` is stale, and
the grace timer is suspended. This is a fail-open in one of the three firewall
modules.

**Fix:** run the cleanup under `NonCancellable` (`withContext(NonCancellable + Dispatchers.Main)`)
or hide the overlay with a non-suspending `Handler(Looper.getMainLooper()).post { ... }`,
and do the map/state cleanup *before* any suspension. Add a test that cancels the
relay scope while a prompt is pending and asserts `promptPending() == false` and
`pendingPrompts == 0`.

### H7 — The approval prompt is tapjackable and can be obscured

**Where:** `ui/CallPromptOverlay.kt:72-76` adds a `TYPE_APPLICATION_OVERLAY`
`ComposeView` with no `setFilterTouchesWhenObscured(true)`; `ui/CallPromptActivity.kt`
does not set it either. A malicious app with `SYSTEM_ALERT_WINDOW` can draw a
transparent overlay above the prompt, show a fake card, and let taps fall through to
the real *Allow once* / *Always allow* buttons. Android 12 blocks some untrusted
passthrough, but not a fully transparent overlay, and the app never opts into
filtering.

**Impact:** the prompt is the authorization UI for a shell capability. A wrong
approval is a policy bypass, and the design does not mention this threat.

**Fix:** call `compose.setFilterTouchesWhenObscured(true)` (API 31+) on the overlay
and on the activity's root view; optionally add `FLAG_SECURE`. Document the
remaining overlay risk. Add a device test that an obscured touch does not approve.

## 3. Medium findings

### M1 — Silent peers can exhaust the relay

`FirewallProxy` accepts a connection, connects upstream (3 s timeout) and starts a
relay with no read timeout. A peer that can reach the VPN address and passes the IP
allowlist can hold all 8 connection slots by connecting and sending nothing; the
accept loop is also blocked for up to 3 s per connection on the upstream connect.
The design's "DoS resistance" claim only covers frame sizes, not idle connections.

**Fix:** set `soTimeout` on the client socket for the pre-`A_CNXN` phase (e.g. 10 s),
close a connection that sends no frame within the timeout, and cap pre-auth
connections separately from established ones. Add a test with a silent socket.

### M2 — The documented 4 KiB pre-`A_CNXN` cap is not implemented

`AdbFrameCodec.MAX_PAYLOAD` is 1 MiB for every frame, and `readFully` allocates
the full payload before reading it. `docs/FIREWALL.md` §12 says "caps a pre-`A_CNXN`
payload at 4 KiB and any payload at 1 MiB". A peer can force 8 MiB across the 8
connections before auth.

**Fix:** enforce a 4 KiB cap until the connection has sent `A_CNXN`/`A_AUTH` and
1 MiB afterwards; or correct the document.

### M3 — The parsed service string is unbounded in field count

`AdbCallParser.parse` builds one `fields` entry per argv token and per NUL-separated
`abb_exec` argument, with no count cap. A 1 MiB `shell:` command of single-character
tokens creates a huge map that the `call_open` audit event retains (500 events in the
ring), the prompt renders, and "Always allow" persists as a rule in prefs.

**Fix:** cap the service-string length and the field count the relay parses and
retains (e.g. 4 KiB / 32 fields), truncate the audit `fields`, and cap the rule
size. Add a test with a 1 MiB service string.

### M4 — Rule order cannot be changed in the UI

`docs/FIREWALL.md` §7.4 says "The rule list is ordered and the UI supports move
up, move down and delete." `FirewallScreen` has Edit and Delete only, and
`FirewallConfigStore`/`AppViewModel` have no reorder operation. Evaluation is
first-match-wins in creation order, so a broad rule added early can never be moved
below a narrower one.

**Fix:** add `moveUp`/`moveDown` to `FirewallConfigStore` and the rule row, and a
test that the stored order changes.

### M5 — No prompt countdown, and the prompt can be replaced by another

`docs/FIREWALL.md` §7.5 says the prompt shows a countdown. `CallPrompt` shows no
remaining time. `CallPromptOverlay.show()` calls `hide()` first, and
`ControlBus.pendingPrompt` is a single slot, so with two pending prompts only the
last is visible; the earlier one is denied after 30 s without ever being shown.

**Fix:** show the remaining timeout (pass a deadline through `PromptRequest`), and
either queue prompts one at a time with a "1 of N" label or render a stack. Add a
test with two pending prompts.

### M6 — Excess prompts are denied without an audit event

`ControlService.promptForCall` returns `null` when `prompts.size >= MAX_PROMPTS`
without recording `call_denied`. `docs/FIREWALL.md` §7.5 says "excess calls are
denied and audited."

**Fix:** record `call_denied` with `rule="prompt-cap"` before returning `null`.

### M8 — A hardening failure leaves both listeners up and loses the watchdog alarm

`ControlService.watchdog()` catches an `ensureWifiDebuggingOff` failure, calls
`fail()` and returns. The relay and the patched daemon keep running, so the system
TLS listener and the app relay are both up. `ACTION_WATCHDOG` in the `Error` phase
calls `watchdog()`, which returns at `phase != Running` without `scheduleWatchdog()`,
so the 15-minute alarm chain ends. The 60 s loop retries, but there is no backoff.

**Fix:** on a hardening failure, stop the relay (fail closed) or at least mark the
exposure and retry with backoff; re-arm the alarm before every early return, and add
a bounded retry/backoff state to the watchdog.

### M9 — The watchdog alarm is lost after any setup error

`ACTION_WATCHDOG` → `resumeAfterRestart()` is false when the phase is `Error`
(it is not `Idle`), then `watchdog()` returns at `phase != Running` without
`scheduleWatchdog()`. A failed setup therefore loses the 15-minute wakeup; only the
in-process 60 s loop remains, and it dies with the process.

**Fix:** schedule the alarm unconditionally in `onStartCommand` for the watchdog
action (or in `fail()`), and keep the backoff state in prefs.

### M10 — `abortSetup` does not verify the TLS listener

`docs/AUDIT.md` P1-9 is still open: `abortSetup` checks the loopback port, not
`service.adb.tls.port` or the closed TLS port. An OEM that ignores the write during
cleanup is not noticed. Related to H3.

**Fix:** reuse `WirelessDebuggingGuard.ensureOff()` (or its read/verify half) in
`abortSetup` and report the failure in the error text.

### M11 — The loopback channel can be spoofed

`docs/AUDIT.md` P1-14 is still open. `probeDaemon`/`verifyDaemon` accept any
process on `127.0.0.1:<loopback>` that answers `id` with `uid=2000`. A malicious
local app that binds the port first can receive the developer public keys and the app's
shell commands, and the app reports Running. `SystemAdb.ensureConnected` has the same
problem for `lastTlsPort`/`listeningShellPorts`.

**Fix:** prove the daemon's identity: a per-install random token in an app-private
file that the daemon signs, a binary hash check, or an app-private unix socket instead
of a predictable TCP port. For the system adbd, pin the TLS certificate it presented
during pairing.

### M12 — VPN address selection is a name heuristic

`Endpoint.chooseVpnAddress` only accepts interface names starting with `tun`, `ppp`,
`wg` or `utun`. A VPN with another name (`vpn0`, `ipsec0`, a branded interface) is
missed; a stale `tun*` interface from another VPN is picked. `VpnDetector` falls back
to scanning every interface when `ConnectivityManager` has no VPN network.

**Fix:** use the `TRANSPORT_VPN` network's `LinkProperties` (already the primary path)
and do not filter by name; validate the address is IPv4, not loopback/link-local, and
belongs to the active VPN network. Add a test with a `vpn0`-named interface.

### M13 — `debugVpnIp` is honoured in release code

`VpnDetector.currentVpnAddress` reads `prefs.debugVpnIp` without a `BuildConfig.DEBUG`
check (`MainActivity` only sets it in debug). The design says "a release build never sets
it". A debug install and a release install cannot share data (different signatures), so it
is not exploitable today, but the release code path should not honour a debug override.

**Fix:** gate the read on `BuildConfig.DEBUG`.

### M14 — `QrScanner` leaks the camera when the dialog is dismissed

`docs/AUDIT.md` P1-16 is still open. `DisposableEffect` only shuts down the executor;
`bindToLifecycle(lifecycleOwner, ...)` uses the activity's lifecycle, so dismissing the
`AddKeyDialog` leaves the camera bound and the indicator on until the activity is destroyed.

**Fix:** call `provider.unbindAll()` in `onDispose` (or bind to a custom lifecycle that
follows the composable), and `await` the provider off the main thread.

### M15 — The app allowlist can be enabled without `UsageStats` or with an empty list

`FirewallScreen` toggles the module regardless of the appop and the list. The design says
the UI prevents enabling it with an empty list, or shows a persistent warning if it is
already enabled; and the module cannot be enabled without `UsageStats`.

**Fix:** disable the switch when the appop is missing and show the grant action; require a
non-empty list; show a warning when either is missing.

### M16 — The IP allowlist can be enabled with an empty list

Same for `ipAllowlistEnabled`: enabling it with an empty list denies every peer, and the UI
neither prevents it nor warns.

**Fix:** disable the switch when the list is empty, or show a warning.

### M17 — `MdnsDiscovery` mutates a `LinkedHashSet` from two threads

`ports` is mutated in `onServiceResolved` (binder thread) and read in `finish()` (main
thread). A resolve that lands during the timeout can be lost or throw.

**Fix:** use a concurrent set or synchronize the access.

### M18 — The relay's `closed` flag is not thread-safe

`AdbRelay.closed` and `FirewallProxy.Connection.closed` are plain `Boolean`s written by
both directions and by `closeAll`/`onClose`. A double close double-decrements `perPeer`
and calls `onClose` twice, which can drop the per-peer count below zero and allow more than
two connections from one peer.

**Fix:** use `AtomicBoolean`/`synchronized` around `close()`.

### M19 — The daemon's logs are unbounded

`docs/AUDIT.md` P1-8 is still open. `adbd.log` and `adbd.stderr` are appended in
`/data/local/tmp/adb-anywhere` with no rotation; the app's `tail` is bounded but the
files are not. A noisy peer can fill the phone's storage.

**Fix:** cap and rotate both files in `DaemonManager`/the daemon (`--log`), and document the
retention.

### M20 — `Shell` timeouts do not cover a hung read

`docs/AUDIT.md` P2-10 is still open. `execV2` checks the deadline only after a frame is
read; a hung command blocks the IO coroutine and `setupMutex`.

**Fix:** set `SO_TIMEOUT` or run the read under `withTimeout` and close the stream on
timeout.

### M21 — `adbd` still accepts `dev:`, `dev-raw:`, `local*:`, `acceptfd:` and `vsock:`

The design's patch table says the kept services are `shell:`, `exec:`, `abb_exec:`,
`sync:`, `tcp:`, `reverse:` and `framebuffer:`, and that vsock is disabled. The patched
`service_to_fd` still accepts `is_socket_spec` (which includes `vsock:`, `acceptfd:` and
`local*:`) and `dev:`/`dev-raw:`. The relay's `AdbCallParser` denies them only when call
policy is on; with it off they are forwarded. The daemon runs as `shell`, so this is not a
privilege escalation, but it is a design-conformance and audit gap.

**Fix:** either remove those branches in the patch, or add them to the design and the
relay's supported set; add them to the built-in denies.

### M22 — `README.md` claims wildcard binds are refused

`README.md:107` says "Wildcard binds are refused." The patched `adbd` accepts any
`--listen` host, including `tcp:0.0.0.0:<port>` (`adbd/patches/09-socket_spec.cpp.patch`
`listen_on_host`). The app never passes one, but the claim and DESIGN.md §2's "the app is the
only entity that controls the ADB listener" are not enforced by the daemon. A shell user can
start a second daemon with any listen spec and read/write the key file.

**Fix:** reject `0.0.0.0`, `::` and empty hosts in `listen_on_host` (or in the `--listen`
parse), and state in DESIGN.md §2/§8 that a shell user can start a second daemon and rewrite
the key file, so the app is not the only controller.

### M23 — `docs/FIREWALL.md` §16 deferred `auth_ok`/`auth_unknown` audit events

Related to H5: the audit log cannot attribute a call to a key, so an incident cannot be
reconstructed from the log. The design says the relay never authenticates, but the relay can at
least record the `A_AUTH` key fingerprint and whether `A_CNXN` followed.

**Fix:** parse `A_AUTH` and record `auth_unknown` (key fingerprint, peer) and, on the server's
`A_CNXN`, `auth_ok`. Add the key label to the prompt.

### M24 — Editing a rule with an unlocked field silently re-locks it

`ui/RuleEditor.kt`: `fixed` is built from every predicate field, including `AnyValue`, and
save turns each fixed field into `Exact`. A rule edited from the list therefore becomes narrower
than the user sees. This is not a security bypass (it fails closed), but it is a correctness bug.

**Fix:** build `fixed` from `Exact`/`Prefix`/`Glob` predicates only, and test round-trip of an
`AnyValue` predicate.

### M25 — The prompt notification is not cancelled when the prompt ends

`ControlService.promptForCall`'s `finally` hides the overlay but does not cancel
`Notifications.PROMPT_ID`. A stale "ADB call needs approval" notification remains after the call
is decided or timed out; a tap opens `CallPromptActivity`, which finishes immediately.

**Fix:** cancel `Notifications.PROMPT_ID` in the `finally`.

  `lifecycleLock`, and the `stopSelf(startId)` handoff are careful and tested.

  clears on screen-off/lock.

## 8. Open questions for the owner

1. **Failure-path exposure**: on a failed setup after the Wi-Fi bootstrap,
   should the app fail closed (turn wireless debugging off and verify it) or keep
   it as the recovery path with a bounded retry? The current code keeps it and
   has no retry on a first run. The design's I1 says "remove a fallback last";
   the security model says the system adbd must not be reachable over TCP.
2. **Prompt attribution**: is the deferred key fingerprint in the prompt still
   acceptable, or should the relay parse `A_AUTH`/`A_CNXN` and refuse unauthenticated
   `A_OPEN`s? The answer changes whether the firewall is a real second factor.
3. **Shell-writable key file**: is the shell user's ability to rewrite the key file
   an accepted limitation, or should the app move the key file to an app-private
   location the daemon reads through a private socket? Without root, the daemon runs
   as shell, so the app cannot make the file shell-unreadable.
4. **`sync:` depth**: should the relay track every sync frame (correct, more code)
   or keep the first-frame rule and document it as a limitation? The first-frame
   rule is a bypass today, so I recommend tracking every frame.
5. **Rule reorder**: is first-match-wins order by creation time acceptable, or is
   move up/down required before calling the firewall complete?
